# Immediate Post-Unwedge Re-Share and Standard-Only Receive-Side Recovery — Implementation Plan

> **For agentic workers:** Implement task-by-task with focused tests before broader
> verification, following the repository verify-first discipline.

**Goal:** Implement GitHub issues #477 (sender-side immediate Megolm re-share after
Olm unwedge) and #478 (receive-side standard-only room-key recovery state machine
with actionable terminal guidance) as a single PR.

**Architecture:** Both sides stay Rust-owned. #477 is SDK-led: the crypto machine
detects a newly accepted inbound Olm session (the standard unwedge signal) and
immediately re-queues the current Megolm sessions previously shared with that
device, through the existing crypto request machinery. #478 is Koushi-led: a
typed recovery operation keyed by room + Megolm session runs the ordered standard
sources (local store → trusted backup → own verified devices → Olm unwedge →
sender re-share wait → local retry) and settles to recovered or an actionable
terminal state. Diagnostics coordinate with #459/#476 schemas; no peer key
requests, no peer-forwarded keys, no custom wire events, no policy weakening.

**Tech Stack:** Rust, matrix-rust-sdk (vendored submodule), matrix-sdk-crypto,
koushi-sdk, koushi-core, koushi-diagnostics, React/TypeScript (display only).

## Global Constraints

- Implement #477 and #478 only. No peer `m.room_key_request`, no acceptance of
  peer `m.forwarded_room_key`, no custom wire event, no blind repeated
  broadcasts, no Megolm rotation to recover Olm delivery, no new device/account
  as a shortcut, no weakening of verification/membership/blacklist/history/
  withheld policy, no arbitrary historical peer forwarding, no claim that
  ciphertext recovers when no holder has the key.
- Diagnostics never contain room/user/device/event/session/request IDs, sender
  keys, deterministic hashes, homeservers, display names, message content,
  ciphertext, key material, Recovery Keys, paths, or raw SDK/server errors.
- SDK changes committed in the vendored submodule; root gitlink updated;
  `node scripts/check-sdk-submodule.mjs` green.
- Existing E2EE behavior and Matrix interoperability unchanged.

## Part 1 — #477: immediate re-share after Olm unwedge (sender side)

### Current SDK behavior (verified)

- `olm/account.rs` increments a known sender device's `olm_wedging_index` when a
  new inbound Olm session is created (`SessionType::New`), and the comment
  states this causes re-sharing on the next `share_room_key` pass.
- `share_room_key` already re-shares when
  `ShareState::Shared { olm_wedging_index }` is older than the device's current
  `olm_wedging_index` (`session_manager/group_sessions/mod.rs`), but only runs
  when Koushi next sends in that room.
- `OutboundGroupSession` tracks per-device share state
  (`shared_with_set`, `get_share_state`, `has_pending_share`) and pending
  to-device requests (`to_share_with_set`, `pending_request_ids`).
- `GroupSessionCache` (per machine) holds the active outbound sessions.

### SDK changes

1. **Unwedge signal** — in `machine/mod.rs::receive_encrypted_to_device_event`,
   after a successful decrypt whose `decrypted.session` is `SessionType::New`,
   look up the sender device by curve key; if known and not dehydrated, append
   an internal `OlmRecoverySignal` (device identity, internal only) to a list
   returned with `receive_sync_changes` (alongside the existing
   `room_key_updates`). No tracing-string parsing.
2. **Post-sync safe re-share (matrix-sdk layer)** — the to-device response
   processor collects the signals (`to_device::Output` sidecar →
   `BaseClient::process_sliding_sync_e2ee` → `SlidingSyncResponseProcessor` →
   `process_and_take_response`); after room state for the sync is applied (so
   current membership, including same-sync leaves, is authoritative), the SDK
   runs a bounded pass per signal:
   - resolve the device; `ignored_unknown_device` / `ignored_dehydrated` if
     unknown/dehydrated;
   - find affected rooms via a new `GroupSessionManager` method that scans the
     in-memory active session cache for sessions whose
     `get_share_state(device)` is `Shared { olm_wedging_index }` with
     `olm_wedging_index < device.olm_wedging_index`;
   - for each affected room (bounded per signal), call a new
     `Room::reshare_unwedged_key(device)` that mirrors the normal share path's
     serialization: `spin_lock_store` + `group_session_deduplicated_handler.run(room_id)`,
     then `BaseClient::reshare_unwedged_room_key(room_id, device)` and send +
     mark each returned request exactly like the room send path
     (`room/mod.rs:2499-2507`). Waking `send_outgoing_requests` alone is NOT
     sufficient because group-session requests are not part of
     `OlmMachine::outgoing_requests()`.
   - `BaseClient::reshare_unwedged_room_key` resolves members + settings via
     `room_key_share_context` (state store, current membership) and calls a new
     crypto method `GroupSessionManager::reshare_unwedged_room_key`:
     - loads the EXISTING outbound session only (`get_or_load`, no create);
     - no_matching_session unless `Shared` with an older wedging index;
     - `already_pending` if `has_pending_share(device)`;
     - runs `collect_session_recipients(members, settings, session)`; if
       `should_rotate` (any policy cause: membership/settings/device change)
       → skip with `policy_blocked` and leave rotation to the normal send path
       (rotation is never performed solely to recover Olm delivery);
     - `policy_blocked` if the device is no longer in the allowed recipients
       (blacklist/dehydrated/trust/membership);
     - otherwise `encrypt_for_devices([device], session)` at the session's
       current ratchet (never earlier history), save, return the queued
       requests → the caller sends and marks them.
   - diagnostics recorded per room and per signal.
3. **Diagnostics** — extend `RoomKeyDiagnosticHub` with closed counters/tokens:
   - `olm_recovery_signal = observed | ignored_unknown_device | ignored_dehydrated | failed`
   - matching active outbound-session count bucket (0/1/2-5/6-20/21+)
   - `reshare = queued | already_pending | no_matching_session | policy_blocked | failed`
   - queued recipient count, outgoing request accepted/failed, elapsed bucket
     from signal to queueing.
   Emitted via the existing observer + aggregate counters (see #476 pattern).
4. **Public surface** — `OlmMachine`/`Encryption` exposes the counters snapshot
   and the observer registration (extend the existing
   `set_room_key_diagnostic_observer`); no new wire behavior.

### Koushi (#477)

- The machine hook runs inside sync processing, so no separate Koushi hook is
  strictly required for queueing; Koushi must ensure the outgoing request pump
  runs promptly after sync returns (the existing sync loop already flushes
  outgoing requests). Register/extend the observer during session restoration
  (same point as #476) and record the #477 diagnostics into
  `koushi-diagnostics`.

### #477 tests (SDK crypto + SDK)

1. Alice shares an active session with Bob's device; simulate Bob's failed
   delivery + fresh session + `m.dummy`; assert the same session is re-queued
   for Bob without another room message.
2. No re-share for a device never authorized (no share state).
3. Blacklisted/dehydrated device → `policy_blocked`, no request.
4. Preserved index: re-share content cannot decrypt messages before the current
   session index (assert `first_known_index` ≥ stored share index).
5. Replayed signal → `already_pending` dedup (no duplicate pending request).
6. Multiple active sessions processed in one bounded pass; rotated/historical
   sessions without current proof are not forwarded.
7. Same-sync leave-plus-unwedge: a user who leaves in the same sync is not
   re-sent the current session (membership from the current state store).
8. Privacy tests for the new counters/tokens.

## Part 2 — #478: receive-side standard-only recovery state machine

### Current building blocks (verified)

- Koushi: `koushi_sdk::request_room_key_for_event` (SDK `request_room_key`,
  targets own verified devices), `download_room_key_from_backup`,
  `request_late_decryption` (event-cache retry), the #466 per-event
  `decrypt_retry` flow in the timeline actor, and #476 receive diagnostics.
- SDK: `request_room_key` creates the standard `m.room_key_request` and a
  cancellation; `send_outgoing_requests` claims one-time keys (Olm unwedge)
  and flushes crypto requests; the redecryptor late-decrypts on key arrival.

### Rust-owned state machine (koushi-core)

New module `crates/koushi-core/src/recovery.rs` (actor-owned, per timeline):

```
RoomKeyRecoveryOperation keyed internally by (room_alias, session_alias)
States (closed): Detected, CheckingLocal, CheckingBackup, RequestingOwnDevices,
  RepairingOlm, WaitingForKey, KeyReceived, RetryingDecryption, Recovered,
  TemporarilyFailed, AutomaticPathsExhausted, UnrecoverableNoKnownHolder,
  Cancelled
```

- **Eligibility**: only `MissingMegolmSession` UTDs (`TimelineUnableToDecryptReason::MissingRoomKey`
  with a session id). Malformed/unsupported/identity-mismatch/trust-violation/
  authentication-failure/policy-withheld/unknown → existing typed handling, no
  automatic recovery.
- **Coalescing**: one operation per room+session; new matching UTD events join
  the existing operation; at most one backup lookup, one own-device request
  batch, one Olm repair flush, and one retry sequence per operation.
- **Order**: local crypto-store lookup (koushi-sdk exposes a typed local
  `has_inbound_group_session` check) → trusted backup
  (`download_room_key_from_backup`, closed outcomes for absent/unavailable/
  untrusted/transport/imported) → own verified devices (one standard
  `m.room_key_request` via the existing SDK path; wake the request pump;
  cancellation after an acceptable key) → Olm unwedge flush (the SDK's
  `send_outgoing_requests` claim path; no anti-churn reduction) → wait for
  sender re-sharing including #477 → event-cache/visible-timeline retry
  (existing `request_late_decryption` + diff observation).
- **Bounded retry/backoff** owned by Rust (per-operation attempt counter +
  backoff buckets); manual retry starts one fresh bounded attempt after a
  terminal/retryable state.
- **Persistence**: only the minimal safe resume record (room alias + session
  alias + attempt state) in the existing store namespace; no identifiers.
- **Key arrival**: on key stored (observed via #476 ingress/broadcast or
  backup import), persist, trigger `request_late_decryption`, verify UTD
  replacement via timeline diff observation; if stored but visible timeline
  still UTD → bounded local retry only (no new request); `Recovered` only
  after authoritative cache state reflects decryption.
- **Terminal guidance** (typed, rendered by React):
  - `another_own_device` → "Open another verified device and retry."
  - `backup_unavailable` → link to Secure Backup status UI.
  - `sender_reshare_may_recover` → "Ask the sender to send a new message in
    this room, then retry." (never promises rotation/historical recovery)
  - `unrecoverable` → "Ask the sender to repost the unreadable content."
- Integration: the timeline actor owns operations for its room; main/thread/
  open/closed/restart share the same semantics via the actor's existing UTD
  diff observation (#466 settlement) and the per-room operation map.

### Diagnostics (coordinate with #476)

Closed counters/tokens: eligible vs ineligible UTD reason; local lookup
outcome; backup lookup/import outcome; own-device request
queued/sent/cancelled/failed; Olm repair queued/sent/throttled/failed;
waiting/retry count buckets; key received/imported; event-cache retry
requested; matching event count bucket; recovered/still-UTD/local-retry-failed;
terminal reason; elapsed-time buckets.

### Frontend

- Timeline UTD placeholder shows recovery progress (typed state) instead of an
  inert control: "Checking backup…", "Requesting keys from your devices…",
  "Waiting for key…", and terminal guidance text with the four actions.
- React renders Rust-owned state only; no React timers, no outcome inference.
- The existing manual "Request keys and retry" control shows operation progress.

### #478 tests (koushi-core, synthetic)

1. Missing key present locally recovers without network work.
2. Backup import late-decrypts all matching events.
3. Backup absence falls through to one own-device request.
4. Verified own device returns key → remaining requests cancelled + events
   decrypt.
5. No verified own device → exhausted state without a request storm.
6. Wedged Olm queues claim/`m.dummy` + wakes the pump.
7. Multiple UTD events share one operation.
8. Main/thread/open/closed/restart same semantics.
9. Stored key + stale visible timeline → bounded local redecryption only.
10. Malformed/trust-failed/withheld/unsupported never auto-recover.
11. Retry/backoff survives restart without duplicate requests.
12. Manual retry restarts one bounded operation with progress.
13. Terminal guidance distinguishes the four options.
14. No peer request sent / no peer-forwarded key accepted.
15. Synthetic privacy tests.
16. (#477 integration) Koushi sender re-share → recipient late-decrypts.
