## PR A — frontend fixes

### #959 — sender user info in the thread pane

`TimelineView` gates two row handlers on the presentation context:

```
apps/desktop/src/components/TimelineView.tsx:3535-3540
  onOpenSenderProfile={presentationContext === "room" ? onOpenSenderProfile : undefined}
  onStartDirectMessage={presentationContext === "room" ? onStartDirectMessage : undefined}
```

The thread pane renders `presentationContext="thread"`
(`apps/desktop/src/components/rightPanel.tsx:867`) and never receives an
`onOpenSenderProfile` prop in the first place, so both the gate and the wiring
must change.

Decision: the gate is removed entirely. `room`, `thread` and `focused` all pass
the handlers through. The presentation context does not decide whether a sender
has a profile; the row already decides that from `senderProfileUserId`, which
keeps compact continuation rows, system events and missing profiles suppressed
exactly as today.

Wiring: `App.tsx` already owns `onOpenSenderProfile`
(`apps/desktop/src/App.tsx:6122`) and passes it to the main pane through
`panes.tsx`. `rightPanel` gains an `onOpenSenderProfile` prop with the same
`(roomId, userId) => void` contract, forwarded to the thread `TimelineView`.
`onStartDirectMessage` is already a `rightPanel` prop and is forwarded the same
way.

Consequence, accepted: the user info panel and the thread pane are the same
right-panel surface, so opening a profile from a thread replaces the thread
pane with the profile pane, exactly as the main timeline does. No thread-local
profile surface is introduced.

Tests: extend `TimelineView.sender-avatar.test.tsx` and
`TimelineView.interactions.test.tsx` with a `presentationContext="thread"` case
asserting the callback fires with the same `(roomId, userId)` arguments as the
room case; a `rightPanel` test asserting the prop reaches the thread timeline.

### #956 — mention pill caret anchors are traversable caret stops

`renderEditorDocument` (`apps/desktop/src/components/ImeTextControl.tsx:607`)
emits a zero-width caret anchor before a leading mention and after any mention
whose next inline is not text — the #875 fix that gives the caret a real text
box outside the pill's border box. `documentOffsetFromDomPoint` collapses an
anchor to the document offset it sits at
(`apps/desktop/src/components/ImeTextControl.tsx:707-709`), so the engine's
caret advances into the anchor while the document caret does not move and
nothing moves on screen. Two adjacent pills carry three anchors, which is the
three dead presses in the report.

Approaches considered:

1. **Intercept the arrow key at the anchor boundary (chosen).** In the
   contenteditable `onKeyDown`, for `ArrowLeft`/`ArrowRight` with no
   `ctrl`/`alt`/`meta` modifier (`shift` allowed, for selection extension),
   ask a pure helper whether the next caret step in that direction lands on a
   caret anchor. If it does, `preventDefault()` and place the caret (or the
   selection focus, under shift) on the far side of the anchor. Every other
   key, every modified arrow, and every arrow that is not at an anchor
   boundary is forwarded to the browser untouched.
2. Normalize the selection after the fact, on `selectionchange`. Rejected: the
   press has already been consumed, so the dead press remains.
3. Emit fewer anchors. Rejected: the adjacent-pill case is precisely the case
   #875 needs an anchor for, so this reintroduces the painted-inside-the-pill
   defect.

The helper is a pure function over the editor DOM and the current selection:

```ts
caretAnchorSkipTarget(
  control: HTMLDivElement,
  direction: "forward" | "backward",
  selection: Selection
): { node: Node; offset: number } | null
```

It returns `null` — meaning "let the browser move the caret" — whenever the
adjacent node in the travel direction is not a caret anchor. Purity keeps it
unit-testable under jsdom, where native caret motion does not exist.

Composition safety: the handler returns early while `composingRef.current` or
`event.nativeEvent.isComposing` is set, so it never competes with an IME
conversion candidate window that uses arrow keys.

Tests: a focused Vitest suite over `caretAnchorSkipTarget` covering leading
anchor, trailing anchor, the shared anchor between two adjacent pills, a pill
with text on one side, and a caret nowhere near an anchor; plus a Playwright
check in the real engine asserting that with two adjacent pills, three Right
presses from the document start reach the document end. The Playwright check is
the only tier that can observe the native caret, so it carries the regression.

## PR B — Space vertical

### #960 — canonical Matrix name vs local presentation name

Today `SpaceSummary` (`crates/koushi-state/src/state/room.rs:9`) carries only
`display_name`, fed from `MatrixRoomListSpace.display_name`
(`crates/koushi-sdk/src/room_projection.rs:47`), which the SDK computes with
fallbacks to alias and heroes. The canonical `m.room.name` is not represented,
so a Space with a local presentation name shows nothing else anywhere.

Change:

1. `MatrixRoomListSpace` gains `raw_name: Option<String>`, filled from the
   SDK's `m.room.name` state only — never from an alias or a computed name.
2. `SpaceSummary` gains `raw_name: Option<String>` with `#[serde(default)]`, so
   snapshots written before this change still load.
3. `display_name` keeps its present meaning and fallbacks. Nothing that renders
   a Space label today changes behavior.
4. `SpaceInfoPanel` shows two labeled rows: the Matrix canonical name, and the
   local presentation name. When `raw_name` is `None` the canonical row renders
   an explicit "not set" message rather than borrowing the computed name.
5. Editing the local presentation name still writes only local state; no
   `m.room.name` event is ever sent.

Message catalog: new keys `space.canonicalName`, `space.canonicalNameUnset` in
both the `en` and `ja` tables of `apps/desktop/src/i18n/messages.ts`.

### #961 — all Space child rooms with membership status

Source of truth: the vendored SDK already ships an Element X-compatible
`SpaceRoomList` (`vendor/matrix-rust-sdk/crates/matrix-sdk-ui/src/spaces/room_list.rs`)
backed by `/hierarchy`. Its `SpaceRoom`
(`vendor/matrix-rust-sdk/crates/matrix-sdk-ui/src/spaces/room.rs:31`) carries
`room_id`, `name`, `display_name`, `avatar_url`, `join_rule`,
`num_joined_members`, `via` and `state: Option<RoomState>` — everything the
issue asks for, with no fork extension.

Existing scaffolding: the sidebar already has a not-joined lane that is wired
end to end and permanently empty —
`SidebarModel::not_joined_space_rooms` and `SidebarSections::not_joined`
(`crates/koushi-state/src/sidebar.rs:18,33`) are assigned `Vec::new()` at
`crates/koushi-state/src/sidebar.rs:218`, and `Shell.tsx:1018-1033` already
renders the section with a `onJoinRoom` click path and a suppressed context
menu. This work fills that lane rather than inventing a new one.

Ownership and flow:

1. A core-owned space-children projection fetches the hierarchy for the
   selected Space through `SpaceRoomList`, and republishes on space selection
   and on membership-changing events (join, leave, invite received, invite
   declined).
2. Membership is resolved against authoritative local state first: a room
   present in `state.rooms` is `joined`, a room present in `state.invites` is
   `invited`, otherwise the hierarchy's `state` decides, falling back to
   `not_joined`. Rooms whose details the server withholds are reported as
   unknown and are never enriched by working around the server's permission
   model.
3. New state slice `space_children`, keyed by space id, holding the projected
   entries. `RoomListItem` gains `membership: RoomMembershipStatus`
   (`#[serde(default)]`, defaulting to `joined` so existing items are
   unchanged) and the not-joined lane is populated from the projection.
4. Joined entries keep coming from `RoomSummary`, so unread counts, favourite
   and low-priority filters, sorting and selection semantics are untouched for
   every room that exists today.

Sidebar placement: the "Not joined" section moves below the low-priority
section. It is currently rendered first (`Shell.tsx:1019`, ahead of the main
list at 1040, favourites at 1056 and low priority at 1071); it becomes the last
section, so joined rooms keep the top of the list.

Space info panel: the Rooms list renders every child with a status badge —
joined, invited, not joined, unknown — and offers a Join action on the rows
where the join rule and the user's permissions allow it. Join dispatches the
existing `RoomCommand::JoinRoom`
(`crates/koushi-core/src/room/operations.rs:779`); no new join path is written.

Message catalog: new keys for the three status badges and the unknown state, in
both locales. `workspace.notJoined` already exists in both.

Mirrors to update in the same change, per
[state-ownership](../../agents/state-ownership.md): `koushi-state` state and
reducer, `koushi-protocol` contracts, `apps/desktop/src-tauri/src/dto.rs` and
its serialization-contract test, `apps/desktop/src/domain/types.ts`,
`coreEvents.ts`, `coreEvents.generated.json`, the browser transport fixtures,
`tauriIpcMock.ts`, `appHarnessMain.tsx`, and every Rust/TS fixture that builds
`SpaceSummary` or `RoomListItem`.
