## #1348 — scheduled sends followed the default formatting, not the setting

Immediate sends and edits build their content from the composer's live
formatting options; the scheduled-send path did not. The account actor built
delayed content with `build_room_message_content_from_composer_body`, a
`pub(crate)` convenience wrapper that hard-codes
`ComposerFormattingOptions::default()` (`math_mode: true`), so every scheduled
body was formatted with math enabled whatever the setting said.

- `crates/koushi-core/src/account/scheduled_send.rs:64` —
  `build_scheduled_message_content` now takes
  `koushi_state::ComposerFormattingOptions` and calls
  `build_room_message_content_from_composer_body_with_options`, the same builder
  the immediate path uses.
- All three scheduling paths carry the options:
  `ScheduleServerDelayedSend`, `DispatchLocalScheduledSend` (the local
  fallback), and `RescheduleServerDelayedSend`
  (`crates/koushi-core/src/account/actor.rs:209-259` and the dispatch arms).
- The runtime reads the live setting and injects it
  (`crates/koushi-core/src/runtime.rs:2916`,
  `crates/koushi-core/src/runtime/scheduled_send.rs:131`), mirroring how the
  existing `CoreCommand::Timeline` send path obtains
  `self.state.settings.values.composer.formatting_options()`.
- The now-unused default-options wrapper was deleted; the three existing
  `composer` unit tests that used it pass `ComposerFormattingOptions::default()`
  explicitly, which keeps their meaning byte-identical.

Deliberate asymmetry, recorded rather than glossed: server-delayed content is
built when the reservation is created, so it takes the setting in force at
schedule time; the local fallback keeps only the raw body and builds at dispatch
time, so it takes the setting in force then. Both match the immediate-send
behavior, and neither stores a new field in the persisted
`ScheduledSendItem` DTO.

## #1328 — the reported symptom does not reproduce on this base

The issue's own event shape (an Element-authored thread reply: `m.mentions` plus
a non-percent-encoded `matrix.to` anchor whose text has no leading `@`) was
driven through both layers:

- **Rust projection.** Under a thread-focused key the reply keeps
  `mentioned_user_ids == ["@alice:example.test"]`, `is_hidden == false`, and a
  sanitized `formatted.html` containing
  `href="https://matrix.to/#/@alice:example.test"`. Permanent check:
  `crates/koushi-core/src/timeline/manager/thread_mention_projection_tests.rs`
  (`thread_focus_projection_preserves_element_mention_anchors`). It lives
  outside `manager`'s inline test module, which is at the inline limit enforced
  by `scripts/check-rust-test-structure.mjs`.
- **Renderer.** The real thread pane (`ThreadPanel` → `TimelineView` with
  `presentationContext="thread"`), fed through the harness `Timeline`
  `InitialItems` for `threadTimelineKey`, renders
  `a.message-mention-pill[data-mention-user-id="@harness-ada:example.invalid"]`.
  Permanent check: `apps/desktop/e2e/thread-mention-pill.spec.ts`, which also
  keeps the #874/#1123 negative control (identical text without `m.mentions`
  stays plain text and produces no pill).

The pill contract needs two facts — the event's `m.mentions` and a formatted
body whose anchor is marked for that user id — and both are present for this
shape, so the plain-text observation cannot be reproduced from the issue's data.

One **reproducible** gap in the same area was found and deliberately left
unfixed, because it is a different defect from the reported one: a mention
inside a **reply quote**. `ReplyQuote`
(`crates/koushi-state/src/state/room_interactions.rs:74`) carries no mention
ids, and `TimelineItemRow.tsx:847` calls `renderFormattedBody(quote.formatted, [],
…)`, so the quoted anchor renders as an ordinary `matrix.to` link instead of a
pill. A probe asserted the quote produced zero pills and printed
`<a href="https://matrix.to/#/@harness-ada:example.invalid" rel="noopener
noreferrer" target="_blank">Harness Ada</a>`. Fixing it needs a new
`ReplyQuote.mentioned_user_ids` field across `koushi-state` → `koushi-protocol` →
the TypeScript mirror → the renderer, which is a separate change with its own
DTO/contract review; it is not bundled here.

The issue stays open. What is needed to move it forward is production data from
the build that showed the symptom: the affected row's `mentioned_user_ids` and
`formatted` values (or whether the row fell back to the plain `body`), whether
the message had been edited afterwards, and the app build.

## Documentation check

`docs/help/messaging.md` ("Schedule a message") documents send-later behavior
and the server/local delivery labels; math formatting is a composer toggle whose
user-visible strings are product text (`composer.mathMode`,
`composer.mathModeOn`, `composer.mathModeOff`), and no help page documents
formula rendering. #1348 makes a scheduled send behave like the immediate send
it was composed as, so no help page changes are needed — recorded here rather
than silently skipped.
