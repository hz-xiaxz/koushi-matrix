## #1385 — the timeline collapsed under an in-pane scrollable list

**Cause.** The room media gallery and the in-room scheduled card are
content-sized flex children of `.main-pane`, whose default `min-block-size:
auto` let them take their full content height. `.timeline-scroll` (`flex: 1 1
0`) gave up its space first, so the timeline collapsed to 0 and the composer was
pushed past `.desktop { overflow: hidden }` — the reported "media gallery covers
the timeline" and "a couple of scheduled messages and the composer disappears".
The settings room-index list was a third instance with a different cause:
`.settings-detail-list { overflow: hidden }` came later at equal specificity and
overrode `.crawler-room-status-list`, clipping the list instead of scrolling it.

**Fix.** `.main-pane` now defines two local size tokens
(`--main-pane-timeline-min-block-size: 140px`,
`--main-pane-gallery-max-block-size: min(320px, 38vh)`), the gallery becomes
`flex: 0 1 auto; min-block-size: 0; max-block-size: <token>; overflow-y: auto`,
`.timeline-scroll` keeps a floor via
`min-height: var(--main-pane-timeline-min-block-size, 0)`, the scheduled card
becomes `flex: 0 1 auto; min-block-size: 0; overflow-y: auto` so the column gives
it only what the timeline floor and the composer leave over, and the room-index
list is scoped to `.settings-detail-list.crawler-room-status-list` so it wins the
cascade and scrolls.

The scheduled card has no fixed cap on purpose. A first attempt capped it at
`min(240px, 32vh)`, which made
`contextual-actions-layout.spec.ts` "creation and scheduled-edit actions fit in
en" fail: the card's in-place editor put its Save button 25px below the viewport,
because `align-content: start` keeps the card's auto rows at their content height
and the capped box scrolled them out of view. Letting flex shrink do the work
keeps the card content-sized whenever the pane can afford it, so the editor is
never squeezed below its own Save action. That failure was caught by the existing
containment check, not by inspection.

**Checks** — `apps/desktop/e2e/scrollable-list-bounds.spec.ts` (new): three
cases seed a media gallery (1400×700, 80 items), an in-room scheduled card
(1400×620, 11 items) and the settings room-index list (8 crawler rooms), then
measure rectangles and hit-test the last row after a real wheel scroll.

| Check | Pre-fix | Post-fix |
| --- | --- | --- |
| `the room media gallery scrolls inside the timeline pane` | `FAILED` — `scrollHeight === clientHeight` (908), `overflow-y: visible`, timeline pane 0px tall | `ok` |
| `an in-room scheduled card scrolls without collapsing the timeline` | `FAILED` — `scrollHeight === clientHeight` (1097), timeline pane 0px tall at the 620px minimum window | `ok` |
| `the settings room-index list scrolls instead of clipping` | `FAILED` — computed `overflow-y: hidden` | `ok` |

## #1380 — the bundled Twemoji font painted the system emoji

**Cause.** `@sableclient/twemoji-font@1.0.4` declares a cmap format-14 subtable
for exactly four variation sequences (U+00A9, U+00AE, U+2122, U+24C2 with
U+FE0F) and carries no bare U+00A9/U+00AE/U+2122/U+24C2 glyph. WebKit therefore
treats any other `base + U+FE0F` cluster as unsupported by that font and paints
the whole cluster from the next family in `--font-emoji`. The emoji picker emits
the fully-qualified form for 517 of its 1,940 entries, so Koushi's own
"thumbs up" (`U+1F44D U+FE0F`) painted the system artwork next to a bare `👍`
pill that painted Twemoji. `.emoji-picker-item` never used `--font-emoji`, so
the grid always painted the system font even while Twemoji was selected.

**Fix.** `reactionKeyDisplayText` (in `TimelineItemRow.tsx`) strips U+FE0F and
U+FE0E for display and re-adds U+FE0F only on the four inverted bases. It is
display-only: `reaction.key` stays verbatim for `m.relates_to.key` matching, the
reaction tooltip, `send_reaction`, `redact_reaction` and the accessible name,
because Matrix treats `👍` and `👍️` as two different reactions. Picker cells
now use `var(--font-emoji)`.

**Check** — `profile-settings-session.spec.ts` "bundled emoji font paints picker
cells and reaction keys in the form it carries".

| Check | Pre-fix | Post-fix |
| --- | --- | --- |
| pill text for the picker's own keys | `FAILED` — rendered `👍️` and `1️⃣` verbatim | `ok` — `👍`, `1⃣`, `©️` |
| picker cell font with Twemoji selected | `FAILED` — `Inter, ui-sans-serif, …` (system emoji) | `ok` — contains `Twemoji` |
| `send_reaction` payload | (not reached) | `ok` — `reactionKey: "👍️"` verbatim |

## #1378 — the thread summary chip mixed direction inside one string

**Cause.** `formatThreadSummary` interpolated the Rust-owned reply count, the
latest sender label, the preview and the timestamp into one string rendered in an
LTR paragraph, so an RTL value's trailing neutrals resolved against the template:
an RTL sender name ending `42!` had its `!` stranded at the name's right edge
against the `:` separator, and an RTL preview pulled the timestamp into its own
run so the time jumped in front of the preview with the meridiem left at the far
end. This is the established repo bidi precedent (`867f608d`, #1084): remote text
renders in separate `dir="auto"` elements with the separators in JSX.

**Fix.** The chip now renders the sender and the preview in their own
`dir="auto"` elements from catalog template parts (`ThreadSummaryTemplateText`),
and the accessible name — which cannot carry elements — isolates the same two
values with U+2068/U+2069 instead.

**Check** — `apps/desktop/e2e/thread-summary-bidi.spec.ts` (new): four cases
measure rendered glyph rectangles with a `Range` over the chip's text nodes, so
they hold regardless of how the chip is split into elements.

| Check | Pre-fix | Post-fix |
| --- | --- | --- |
| `an RTL sender name keeps its trailing punctuation beside its digits` | `FAILED` — `x("!")=602` right of `x("42")=553` | `ok` |
| `an RTL preview does not pull the timestamp into its own run` | `FAILED` — preview right edge 724 > time left 639 | `ok` |
| `an RTL sender and an RTL preview stay in the template's order` | `FAILED` — sender right edge 700 > preview left 591 | `ok` |
| `an LTR sender and preview keep the plain order` (control) | `ok` | `ok` |

## #1381 — the encrypted-history hint claimed history sharing was optional

The hint read as if sharing past room keys were a choice, while the client
shares them automatically for an invitee and the share can be skipped by the
recipient's or sender's verification decision. The en and ja entries for
`room.historySharedEncryptedHint` and `dialog.inviteHistoryEncryptedShared` now
say the client shares automatically, that the share needs verification on both
sides, that it may be skipped, and that some or all earlier messages can stay
unreadable. `docs/help/rooms-and-spaces.md` states the same. The
non-retroactive entries are unchanged and keep covering the setting itself.

## #1359 — the stale conversation-badge formula

`docs/architecture/overview.md` still documented
`max(unread_count + thread_unread_count, notification_count, highlight_count +
thread_highlight_count)`. The shipped helper is
`koushi_state::room_activity_unread_count` (`crates/koushi-state/src/state/room.rs:399`)
= `unread_count + thread_unread_count`, with the homeserver's
`notification_count` deliberately excluded because it carries no event IDs. The
doc now states that contract and points at the state-machine document. Docs-only
fix; the Rust tests already pinned the helper.

## #1328 — the mention pill did not read as a pill

The reported shape (an Element-authored thread reply whose `m.mentions` carries a
user id and whose formatted body anchors a non-percent-encoded `matrix.to` link
with an unencoded display name) already reaches `a.message-mention-pill`: the
Rust thread projection keeps `mentioned_user_ids` and the sanitized anchor, and
the real thread pane pills it. What the class alone cannot show is how the pill
*paints*, and the reporter's follow-up measurements on the released build located
two presentational defects that the class/attribute guard could not catch:

- **The pill was underlined.** In a formatted body the pill is the `<a>` itself,
  and `.message-body.message-formatted-body a` (specificity 0,2,1) set
  `text-decoration: underline` over `.message-mention-pill` (0,1,0). The plain-body
  pill is a `<span>` and was unaffected, which is why the main-timeline checks
  looked right.
- **The fill was invisible.** `--surface-hover` (`#f2f4f6`) is effectively the
  thread pane's own surface: the pane background is `color-mix(in srgb, var(--brand)
  12%, var(--surface))` = `#e7f0fe`, measured 2.3/255 per channel away from the old
  fill.
- **The label lost the client's mention spelling.** Element writes the anchor text
  without `@` (`>Alice<`), while the composer chip (`ImeTextControl.tsx`) and the
  plain-body pill both read `@Alice`, so the timeline pill was indistinguishable
  from an ordinary link.

**Fix.** `.message-mention-pill` now takes a stronger brand tint
(`color-mix(in srgb, var(--brand) 22%, var(--surface))`, measured 22.2/255 from the
thread pane, 25.2 from the row, 33.2 from `--surface-hover`) and a class-scoped
`a.message-mention-pill { text-decoration: none }` that outranks the formatted-body
link rule. The formatted anchor renderer prefixes `@` when the anchor text does not
already carry it. That prefix is presentational only: the event's HTML and the
copied plain text keep the sender's spelling, and the negative-control rows in the
specs pin that the unmentioned text stays unprefixed. The prefix is deliberately
*not* paired with `dir="auto"` on the anchor: the composer chip has none either, so
`@` stays at the visual start for an RTL name, which is what "consistent with the
composer" means here.

**Checks.** `e2e/mention-pill-rendering.spec.ts` (room context) and
`e2e/thread-mention-pill.spec.ts` (thread context) now read the rendered paint
through the shared `e2e/support/mentionAppearance.ts` probe; a unit case in
`TimelineMessageBody.test.tsx` pins the prefix and its no-doubling rule.

| Check | Pre-fix | Post-fix |
| --- | --- | --- |
| `TimelineMessageBody` "spells an Element-shaped mention anchor like the composer's chip" | `FAILED` — `>Alice</a>` | `ok` |
| room context "an Element-shaped mention reads as the composer's pill, not as a link" | `FAILED` — `text-decoration-line: underline`, text `Harness Ada` | `ok` |
| thread context "the thread pane's pill reads as a pill against the pane" | `FAILED` — 2.28/255 from the pane surface | `ok` — 22.2/255 |
| thread reply pill text | `FAILED` — `Harness Ada` | `ok` — `@Harness Ada` |
